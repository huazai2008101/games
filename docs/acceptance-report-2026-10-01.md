### 1.3 主要问题(Top 10,详见第 2 节)

1. **P1 中国象棋开局即"引擎异常终止"**——该游戏当前完全不可玩。
2. **P1 内容运营(内容位)模块不可用**——创建强制 draft 且列表不渲染,运营配了 Banner 大厅也永远看不到,后台自己也看不见。
3. **P1 提现驳回无玩家通知**——资金被退回但玩家不知道发生了什么。
4. **P1 玩家侧没有对局记录**——玩家答不出"我刚玩了什么、输了还是赢了"。
5. **P1 admin 玩家管理无搜索/筛选**——玩家量增长后后台不可运营。
6. **P1 UI 自动化测试资产几乎为零**——核心玩法回归完全依赖人工清单。
7. **P2 老虎机 spin 无超时兜底**——结果丢失即永久"转动中"。
8. **P2 游戏缩略图体系失效**——外链被 CSP 拦截、无上传能力,大厅永远是占位图。
9. **P2 表单校验双标**——资金表单(调账)校验优秀,内容表单(游戏编辑)无必填校验且后端对空值静默成功。
10. **P2 新玩家零体验金**——注册即 0 余额,最低注 10,不充值无法体验任何游戏。

### 1.4 主要风险

| 风险 | 说明 |
| --- | --- |
| 回归风险 | e2e/ 仅 2 个冒烟 spec 且真实登录被 .skip;文档驱动的人工回归不可持续 |
| 运营风险 | 内容位不可用 + 玩家无检索 + 充值档位硬编码,运营"接手即可用"不成立 |

| 工程风险 | final_schema 与增量迁移已漂移(version 列、type CHECK),全新建库会缺列 |

### 1.5 主要缺失功能(现状不存在)

- 玩家侧对局记录/战绩页(含回放入口引导)
- 玩家通知触达:提现审核结果、游戏维护公告(通知表已存在,仅缺触发点)
- 后台:管理员禁用/密码重置、玩家批量操作、任意列表导出
- 充值档位/支付渠道后台配置(现硬编码 6 档,`payment.go:22-23`)
- Jackpot/奖池:**不存在**(老虎机无奖池)。按"不过度设计"原则,当前规模**暂不需要**,不建议排期。

### P1-1 中国象棋开局即引擎异常终止
```text
问题:中国象棋两名玩家匹配成功、棋盘渲染后数秒内,双方同时收到"对局已终止:游戏引擎异常导致对局终止"。
当前行为:开局→红方行棋界面出现→立即终止;客户端控制台 TypeError: Cannot read properties of null (reading 'c') 连续 58 次,
      并伴随 "drift detected: no broadcast for 30s / turn deadline passed"。
预期行为:对局正常进行;若引擎异常,应仅终止当前局并在同房间提示重开,且给出可上报的错误码。

严重程度:P1(单游戏不可用;无资金风险——象棋为积分制不动钱包)
建议方案:1) 修复前端 null 棋盘渲染分支与后端 bundle 开局异常(优先查 game-api 日志 14:0x 时段 xiangqi panic);
      2) 引擎异常时客户端上报 roundId+错误码,客服工单可凭 replay 时间线仲裁;
      3) 增加一条 e2e:双上下文匹配→各走一步→断言局面同步。
是否需要后端修改:是  是否需要数据库修改:否  是否需要前端修改:是  是否需要重构:否(定位修复)
推荐实现方式:先在本地 docker 起全栈复现,抓 game-api 日志定位 bundle 抛点;前端对 board 空态加渲染守卫。
证据:b32(棋盘已渲染)、控制台错误清单、b33(终止弹窗)
```

### P1-3 提现驳回无玩家通知
```text
问题:提现被后台驳回并自动退款后,玩家通知中心只有"提现申请已提交",没有驳回通知。
当前行为:退款到账(流水 withdrawal_refund)但玩家无感知,需自己翻提现记录才能发现被驳回。
预期行为:驳回时同步产生站内通知(标题+驳回原因+退款金额),通知中心未读徽标 +1。

      content 带驳回原因与退款金额。
是否需要后端修改:是(一行级)  是否需要数据库修改:否  是否需要前端修改:否  是否需要重构:否
推荐实现方式:复用提现提交时的通知写入函数;顺手补 approve/paid 两个状态的通知(同一处 switch)。
证据:b23(仅提交通知)、后台驳回记录 a36
```

## 4. 后台管理优化方案(逐模块)

> 原则:每条都回答"解决什么问题、谁用、多高频"。标注【保持】的为当前设计合理,明确不改。

### 4.1 Dashboard(仪表盘)
- 现状:3 个计数(开发商/游戏总数/待审核版本)+ 6 个待办入口 + 账号信息。
- 问题:运营首屏回答不了"平台今天怎么样";而数据看板有完整 KPI,两页割裂。
- 方案:仪表盘顶部增加一行"今日"摘要条(今日新增玩家/今日局数/今日充值/待处理提现/待审核包),数据直接复用 /api/admin/analytics 的当日聚合,不加新接口。点击跳转数据看板。
- 收益:运营 5 秒判断平台状态;改动一个组件。【P2】

### 4.2 用户(玩家管理)
- 搜索/筛选(P1-5);玩家详情:现列表行内四个动作(调账/流水/冻结/封禁)已覆盖高频操作,【保持】;不再单建玩家详情大页,避免过度设计。
- 冻结/封禁执行前弹窗需显示当前余额与进行中提现(数据已有),防误操作。【P3】

### 4.3 游戏(内容生态)
- 游戏编辑表单补校验(P2-9);缩略图走 minio 上传(P2-8)。
- 分类删除守卫(P3-30)。
- 审核历史:【保持】按游戏查看版本列表即可。

### 4.4 玩法
- 玩法参数(底分/赔率)为"配置即代码",随版本包固化并经审核——**这是本平台最正确的决策之一,【保持】**,不做运行时参数后台(避免配置生效时机一类问题)。

### 4.5 订单/流水/回合
- 提现审核列表玩家列修复(P2-10);驳回弹窗【保持】(原因必填+自动退回提示,设计优秀)。
- 流水/回合操作双账本【保持】,这是资金核对的基础设施。

### 4.6 Jackpot
- 系统无 Jackpot。以当前 4 款游戏与积分制玩法,**不需要**,不排期(避免为行业对标而堆功能)。

### 4.7 运营(内容位/券)

### 4.8 配置

### 4.9 权限

## 16. 结语:做得好的地方(避免只看问题)

1. **资金正确性是本系统最强的部分**:两阶段回合结算、canonical 锁序、requestId 幂等、余额版本单调守卫、CHECK>=0、崩溃 reaper——实测调账/签到/任务/提现驳回四条资金路径全部账实相符。
2. **提现闭环体验完整**:申请即冻结、驳回必填原因、自动退回、审计留痕——许多成熟平台都做不到这个完整度。
3. **"配置即代码"规避了一整类配置生效时机问题**,审核+RTP 申报+T+1 漂移检测形成了合规证据链。
4. **合规意识完整**:KYC、绑卡、日限额只能下调、自我排除冷静期、注销约束——作为平台骨架是对的。
5. **斗地主的托管/解散/续局**与服务端状态机说明多人游戏骨架是认真做的。
6. 后台空态、确认弹窗、双账本、审计明细等细节可见工程审美在线。

**一句话总结**:地基(资金、状态机、权限、审计)是过硬的;当前最缺的不是新功能,而是把三条"走不通的路"修通(象棋、内容位、对局记录),并把运营日常(找人、通知、图片)补齐。
