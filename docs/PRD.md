## 1. 产品概述

### 1.1 一句话定位

一个**资金安全级**的 H5 即开游戏聚合平台——玩家 3 秒开玩、开发者 10 分钟接入、运营每一步可配置可度量可回滚。

### 1.2 愿景

让任何小游戏团队用最低成本把作品变成可持续收益，让玩家在任何一个页面都能"点开即玩、每一分钱可追溯"。平台的护城河不是某一款游戏，而是**资金可信 + 分发效率 + 接入体验**三件事的行业标杆。

### 1.3 北极星指标与护栏指标

| 类型 | 指标 | 定义 | 目标 |
|---|---|---|---|
| 北极星 | WAEP（周有效游玩玩家） | 周内完成 ≥1 个成功结算回合（`game_round` 落账）的独立玩家数 | 环比 +10%/月 |
| 护栏 | 结算差错率 | 余额对账不平的回合数 / 总回合数 | **恒等于 0** |
| 护栏 | 余额类客诉率 | 余额争议工单 / WAEP | < 0.05% |
| 护栏 | 首局转化率 | 注册 → 完成首局的比例 | ≥ 60% |
| 护栏 | 留存 | D1 / D7 | ≥ 35% / ≥ 15% |
| 护栏 | 支付成功率 | 支付成功订单 / 发起订单 | ≥ 95% |
| 护栏 | 审核时长 | 包提交 → 审核完成 P75 | ≤ 24h |

选择理由：WAEP 衡量的是"真实玩过"而非"打开过"，过滤了拉新水分；结算差错率作为一票否决护栏，是"资金安全级"定位的量化表达。

### 1.4 产品原则

1. **资金安全 > 合规 > 体验 > 功能数量**。任何功能与资金/合规冲突时让位。
2. **移动优先**：首屏到可玩 ≤ 3s（P75）；断线可恢复；异常重来不多扣一分钱。
3. **每一分钱可追溯**：玩家资金变动必有 `round_id` / 幂等键 / 流水；运营动作必有审计与灰度。
4. **双边都要"赚到了"**：玩家获得体验与公平，开发者获得收益与数据，缺一边平台不成立。
5. **合规是硬约束**：实名、限额、公平性公示不是配置项，是底线。

### 1.5 竞品校准

| 对标类型 | 代表形态 | 可借鉴 | 本平台差异化结论 |
|---|---|---|---|
| H5 游戏中心（4399 类） | 海量轻度 H5、强分类导航 | 即开体验、分类分发效率 | 不做海量换皮分发，走"少而精 + 运营位"路线 |
| 海外休闲聚合（Poki / CrazyGames 类） | 免费即开 + 广告变现，开发者自助入驻成熟 | 开发者门户、接入体验、游戏健康度报表 | 变现以流水分成替代广告分成，开发者收益更直接 |
| 真金棋牌 / 电竞平台 | 充提闭环成熟、赛事运营强 | 资金合规设计、负责任游戏工具、赛事体系 | 公平性公示（RTP 存证、真实播报）作为核心信任卖点 |

结论：本平台与任何一类都不正面重叠——用"资金可信 + 公平性公示"做需求侧壁垒，用"开发者 10 分钟接入 + 高分成"做供给侧壁垒。

## 2. 用户画像与核心旅程

### 2.1 用户画像

| 画像 | 目标 | 痛点 | 关键场景 | 设计启示 |
|---|---|---|---|---|
| 休闲玩家·小林（22 岁，学生/白领，碎片时间） | 摸鱼时来两局，放松解压 | 下载太重、加载慢、规则复杂、怕乱扣钱 | 通勤/午休打开大厅 → 热门游戏 → 即开即玩 | 3 秒可玩、无强制引导、余额变动透明 |
| 沉浸玩家·阿凯（28 岁，有稳定娱乐预算） | 追大奖、攒荣誉、比排行 | 玩了没积累、大奖没感觉、平台不透明 | 晚间连续游玩 → 冲榜 → 参与活动 | 成长体系、播报与榜单、公平性公示 |
| 游戏开发者·像素社（2-5 人独立团队） | 上线作品、拿到分成、看数据 | 接入文档烂、审核黑盒、结算不清、没数据 | 注册门户 → 传包 → 提审 → 迭代 → 收款 | 自助门户、审核状态透明、按 round_id 出账单、SDK 10 分钟跑通 |
| 平台运营/审核·老周（平台员工） | 高效配活动、快速审包、控风险 | 工具零散、操作怕出错、出事无据可查 | 配 Banner → 审核包 → 处理风控案件 → 对账 | 配置化 + 审计 + 灰度三件套、风控工作台、对账工具 |

### 2.2 核心旅程（文字版泳道）

```
玩家线    注册(≤30s) → 实名分级 → 浏览/搜索 → 进游戏(≤3s) → 首局(≤1min)
          → 首充(≤3min) → 持续游玩/成长 → 提现(T+1) → 复访(收藏/推荐)

开发者线  注册开发者 → 资质提交 → 创建游戏 → 上传包(bundlesec 校验)
          → 提审(≤24h) → 上架 → 看数据 → 月度分成到账

运营线    配置内容位(定时/灰度) → 审核包 → 配置活动(模板)
          → 监控看板/风控案件 → 迭代策略

管理员线  创建开发者/角色(RBAC) → 监督审核与大额调账
          → 财务对账(round_id 溯源) → 审计留痕检查
```

每个旅程的失败分支在第 4 章各模块"异常分支"中展开。

## 4. 分模块详细设计

> 统一结构：目标 → 用户故事（含验收）→ 页面/交互 → 业务规则（含异常）→ 依赖现有能力 → 数据变更 → 埋点 → 开放问题。

### 4.1 账户与身份

**目标**：注册无摩擦、找回自助、多端可控、注销合规，且绝不触碰 RBAC 域。

**用户故事**
- US-A1 玩家 30 秒内完成注册。验收：注册表单 ≤3 字段起步；提交到登录态 ≤2s；重复用户名/邮箱返回 409 且提示可读。
- US-A2 忘记密码可自助找回。验收：邮箱验证码 10 分钟有效、5 次/小时限频；重置后旧 JWT 全端失效（对齐现有 logout 撤销机制）。
- US-A3 玩家绑定手机号（P1）。验收：换绑需旧手机验证；绑手机后可用手机号登录。
- US-A4 同一账号多端登录互踢。验收：B 端登录成功后 A 端 WS 收到 `session:kicked` 系统事件并回到大厅；对局中被踢提示"账号在其他设备登录"。
- US-A5 玩家可注销。验收：注销需二次确认+无未完成提现单；账户置 `deleted`，昵称/头像清空，但 `player_transaction`/`game_round` **保留**（财务对账要求），拒绝再次注册同身份证（合规）。

**页面/交互**：Login/Register 改版（第三方登录位预留）、找回密码页、Profile 增"账号与安全"（绑定/设备管理/注销）。

**业务规则与异常**：注册触发登录限流（复用现有 loginthrottle）；找回重置后 24h 内禁止提现（风控）；注销复核期 72h 可撤销。

**依赖现有能力**：lobby auth 双 token、loginthrottle、JWT 撤销、双身份域隔离（player 永不进 RBAC）。

**数据变更**：`player` 加列（phone、status 枚举扩展 `deleted`）；新表 `player_identity`（邮箱/手机验证态）。

**埋点**：`register_submit/register_success/login_success/find_password_success/phone_bind_success`。

**开放问题**：三方登录（微信/Apple）渠道资质与合规，M2 评估。

### 4.2 钱包与经济系统（资产闭环，P0 核心）

**目标**：补齐"充值 → 游玩 → 提现"闭环，全部资金路径复用现有幂等/审计/非负约束，**零新增绕过 `player_transaction` 的余额变更**。

**用户故事**
- US-W1 玩家选择档位充值到账。验收：6/30/98/198/328/648 元档位；支付成功到余额 P95 ≤ 10s；到账后游戏内余额经现有 `wallet:balance` 推送实时刷新（version 递增）；流水新增 `type=recharge`（枚举迁移见业务规则）且 `idempotency_key=recharge:{order_no}`；**同一回调重复投递只入账一次**（以渠道交易号幂等）。
- US-W2 平台发放奖励到账。验收：批次发放失败单条可重试且不重复（`idempotency_key=grant:{batch_no}:{player_id}`）；发放/领取均有流水与审计。
- US-W3 玩家申请提现并到账。验收：**提现仅对 KYC Lv2 开放**（人脸核身 + 绑卡，见 4.12-1）；申请即全额扣减余额并出流水（`type=withdrawal`）；驳回自动退回（`type=withdrawal_refund`）；日限 10,000 元（`risk_rule` 配置化）；单笔 ≥50 元，手续费 1%（封顶 10 元）；T+1 审核打款。
- US-W4 财务可对账。验收：任一玩家余额 = 全部流水回放结果；管理后台可按 `round_id`/`order_no` 溯源一笔钱（复用 game_round / game_round_operation / player_transaction 关联）。

**页面/交互**：充值页（档位/渠道/实名引导）、提现页（可提余额/限额/手续费试算/记录）、Profile 流水按 source 筛选（现有流水页扩展）。

**业务规则与异常**
- **流水类型迁移（评审 F3，M1a 迁移项）**：现有 `player_transaction.type` 为 DB CHECK 固定枚举 `('reward','deduct','refund','admin_adjust')`，需迁移扩展 `recharge / withdraw / withdrawal_refund / grant`；充值提现类流水 `game_id/round_id` 为 NULL（符合现有配对 CHECK，评审已核验）。
- 充值：下单创建 `payment_order(created)` → 渠道支付 → 回调验签 → `succeeded` 幂等入账；回调超时走主动查单补偿；掉单（渠道成功/本地未入账）由对账任务兜底补单并告警。
- 提现：申请时余额不足 → 409；命中风控规则 → 转人工案件；打款失败 → 状态 `failed` 自动退回余额并通知。
- 平台发放：批次必须指定预算与有效期，超预算拒绝创建；全程写 `audit_log`。
- 一切入账走 `PlayerBalanceRepo` 写入咽喉（自动携带余额事件推送），**不引入新的写路径**。

**依赖现有能力**：幂等键唯一约束、非负 CHECK、`CommitRound`/`WalletActor`、实时余额推送链路（事务提交后发布）、`audit_log`。

**数据变更**：见第 7 章 `payment_order`、`payment_channel_config`、`withdrawal_order`、`grant_batch`、`grant_item`。

**埋点**：`recharge_order_create/recharge_success/recharge_fail(reason)/withdraw_apply/withdraw_success/grant_issued`。

**开放问题**：体验金/赠送金是否需要与可提现余额拆分（涉及 `player_balance` 结构改造），M2 评估；M1 先以"充值返"代替"体验金"，不引入不可提现子余额。

### 4.3 大厅与游戏发现

**目标**：从"能找到游戏"升级到"3 次点击内想玩的游戏"。

**用户故事**
- US-D1 玩家收藏游戏并在"我的收藏"直达。验收：收藏/取消即时生效；收藏列表按时间倒序；下架游戏在收藏中置灰并标注。
- US-D2 玩家"最近在玩"一键回局。验收：按最近游玩时间倒序展示 ≥3 条；点击直接进游戏。
- US-D3 玩家看到运营推荐位与 Banner。验收：支持定时上下线与权重排序；未到开始时间不可见；点击埋点可归因。
- US-D4 玩家查看富详情页。验收：截图轮播、规则、RTP 声明、在线人数（来自 presence 指标）、开发者署名、举报入口；未审核通过的游戏详情页返回 404。
- US-D5 玩家看到榜单与中奖播报。验收：人气榜（按 `game_round` 聚合轮次，T+0 小时级）、新游榜（上架 ≤30 天）；中奖播报仅展示真实结算回合（从 `game_round` 派生），不虚构。
- US-D6 搜索可用。验收：沿用现有 `gameList` search 参数；空结果展示推荐位；关键词 ≥2 字符触发。

**业务规则与异常**：缓存继续走现有 `GameCacheInvalidator`，新增内容位/榜单缓存同键空间管理；下架/驳回游戏 5 分钟内从所有位消失。

**依赖现有能力**：game_category 主数据、lobby gameList 缓存、game_round 数据、presence 指标。

**数据变更**：`player_favorite_game`、`player_recent_game`、`content_slot`（type=banner/notice/recommend，见第 7 章）。

**埋点**：`banner_click/recommend_click/search(flush keyword)/game_detail_view/favorite_click/recent_click`。

**开放问题**：个性化推荐（行为召回）依赖行为数据积累，M2 起步；P0 用"热度兜底 + 运营加权"。

### 4.4 游戏会话体验

**目标**：把现有可靠的会话底座包装成玩家无感的顺滑体验。

**用户故事**
- US-S1 从点击到可玩 P75 ≤ 3s。验收：bundle 预热（详情页预加载）、连接复用；超时 3s 内给明确重试引导。
- US-S2 断线可自愈。验收：断线 UI 三态（重连中/重连失败可手动/已回大厅）；重连成功后自动对账余额（复用 `balance:query`）；对局中断线 ≥60s 托管规则在游戏侧声明。
- US-S3 游戏内可查规则与战绩。验收：规则抽屉（读游戏配置）、我的战绩（按 `round_id` 列表：时间/局 ID/投入/产出/结果）、余额点击跳转流水。
- US-S4 玩家可举报异常。验收：举报表单（类型/描述/截图）生成工单，附当前 `round_id` 上下文。

**业务规则与异常**：多端互踢见 US-A4；有活跃回合时退出需确认；`session:error` 的玩家话术统一为"本局异常已保护，资金已原路结算"，并给出流水入口。

**依赖现有能力**：actor 会话生命周期、断线重连、余额推送三重对账、`game_round_operation` 失败留痕（客服溯源）。

**数据变更**：无新表（战绩读 `game_round`/`player_transaction`）。

**埋点**：`game_enter_start/finish(duration)/reconnect_success/session_error_show/report_submit`。

### 4.5 多人玩法（房间）

**目标**：补齐房间模式的大厅 UX，让"叫朋友来一局"成立。

**用户故事**
- US-R1 房主创建房间并分享房间码。验收：创建即得 6 位码；分享文案含游戏/模式/码；TTL 内可重复进入。
- US-R2 等待室完整。验收：成员列表/准备状态/房主开始与移人/房主转移；全员准备自动开始（复用现有 ready→playing）。
- US-R3 公开房间可列出可加入。验收：仅展示 `waiting` 且未满员房间；加入已开局房间提示观战（若游戏允许）。
- US-R4 低人气游戏可配置机器人。验收：机器人仅在平台白名单游戏启用、后台可配比例；**对局内明确标识"含机器人陪玩"**（合规要求，不许伪装真人）。

**依赖现有能力**：RoomRegistryActor（roomCode→sessionID）、SessionActor 房主驱动（ownerID）、观战 opt-in。

**数据变更**：`room` 持久化表（房间元信息与统计，可选；运行态仍归 actor/Redis）。

**埋点**：`room_create/room_join/room_share/room_ready/room_start`。

### 4.6 赛事系统（tournament，P2）

**目标**：把预留的 tournament 模式落地，成为平台拉收与传播峰值场景。

**用户故事**
- US-T1 玩家报名锦标赛（报名费走钱包）。验收：报名发生在游戏会话之外（不占用回合语义），扣费走平台单操作资金路径（与管理端调账同源写入咽喉），幂等键 `tournament:{entry_no}`，流水可溯源；满员/截止自动开赛；退款规则在报名页明示。
- US-T2 赛程可查、结果可溯。验收：对阵/积分实时；奖金经平台发放批次（`grant_batch`）到账，公告可查名次与发放记录。

**业务规则**：赛制支持淘汰赛/积分赛；奖金池=报名费聚合+平台补贴（走活动预算）；结算失败进 `game_round_operation` 留痕并转人工。

**数据变更**：`tournament`、`tournament_entry`。

**开放问题**：复用 quick 会话模型还是独立调度器，需技术方案评审后定稿。

### 4.7 成长与激励体系（P1）

**目标**：给"玩"一个可积累的意义，给"留存"一个结构性抓手；所有数值受经济模型约束（第 5 章）。

**用户故事**
- US-G1 玩家有等级与经验。验收：经验 = 有效结算回合 ×1 + 充值金额 ×10；等级阈值曲线 `exp(L) = 100 × L^1.5`；升级即发权益（奖励走 `grant_item`，幂等）。
- US-G2 每日签到。验收：7 日循环 1/2/3/5/8/12/20 元等值金币；断签不清空周期但无递增；补签卡走券。
- US-G3 每日任务与成就。验收：任务池示例（完成 3 局/收藏 1 款/分享 1 次/首充），完成后**手动领取**（防误触发滥用），发放幂等可查。
- US-G4 VIP 体系。验收：VIP 等级按 90 天净流水分档（V1-V6），权益=提现限额提升/专属客服/活动优先；只升不降，档位规则公示。

**依赖现有能力**：`grant_batch` 发放、`player_transaction` 判定有效回合与流水。

**数据变更**：`player` 加列（level/exp/vip_level）；`player_task_log`、`checkin_log`。

**埋点**：`level_up/checkin/task_claim/vip_upgrade`。

**开放问题**：经验是否计入"输局"（防止刷局），M2 用最小局时长阈值过滤。

### 4.8 社交系统（P1 通知 / P2 好友聊天排行）

**目标**：先做"通知中心"这类无风险高价值社交基建；聊天类功能以防骚扰机制先行。

**用户故事**
- US-N1 玩家收到统一通知。验收：系统/交易/社交三类分栏；交易类通知（充值/提现/发放）逐条可点入对应流水或订单。
- US-F2（P2）好友与房间聊天。验收：好友申请-同意模型 + 黑名单；房间文字聊天默认开启敏感词过滤 + 10s/条频率限制 + 一键举报；举报 24h 内响应。

**设计红线**：不做"收益排行榜"诱导攀比；榜单只做人气榜/新游榜/幸运时刻（真实回合播报）。

**数据变更**：`notification`（P1）；`friend`、`friend_request`、`chat_message`（P2，TTL 归档）。

### 4.9 运营与增长系统（P1）

**目标**：运营"不发版"可完成内容、活动、触达三件事，且每一步可灰度、可审计、可回滚。

**用户故事**
- US-O1 运营配置内容位。验收：Banner/公告/推荐位三合一配置（定时/权重/状态）；保存 60s 内大厅生效（跨进程失效广播，见第 10 章依赖）；全部操作写 `audit_log`。
- US-O2 运营用模板创建活动。验收：首批模板（首充返/充值返/亏损救济金/节日签到加倍）；活动实例=模板+时间+人群+预算+库存；预算耗尽自动下线；活动效果看板（参与/核销/ROI）。
- US-O3 运营发券与礼包码。验收：券模板（满减/免单局/补签卡）+ 批量兑换码；核销幂等；支持作废。
- US-O4 运营看数据。验收：看板含 DAU/WAU(WAEP)、留存、充值漏斗、游戏健康度（局均时长/结算失败率/崩溃率——对齐现有 Prometheus 指标）。
- US-O5 灰度发布。验收：关键运营配置支持按玩家百分比灰度；一键回滚 ≤1 分钟。

**依赖现有能力**：`audit_log`、GameCacheInvalidator 模式（扩展为 config 失效广播）、Prometheus。

**数据变更**：`content_slot`（P0 已建）、`activity`/`activity_instance`/`activity_reward_log`、`coupon`/`coupon_redemption`、`player_daily_stat`、`leaderboard_snapshot`。

**埋点**：运营侧事件全部自动采集，活动归因字段 `activity_id` 贯穿到 `grant_item`。

### 4.10 开发者平台（P1）

**目标**：把"管理员代建"升级为自助门户；接入体验以 `examples/slot-game` 为基准，目标 ≤10 分钟跑通 demo。

**用户故事**
- US-V1 开发者自助注册入驻。验收：注册→资质提交（企业/个人）→平台开通账号（复用现有 auto-provision：user→developer→私有角色→权限克隆）；资质驳回有明确原因。
- US-V2 开发者全自助发游戏。验收：创建游戏（选分类）→上传前端包/后端 JS→bundlesec 即时反馈→提审→状态/驳回原因可见；每步无需平台人工介入（除审核）。提审采用增量模式：首个版本必须同时提交前端包与后端包，后续版本仅提交变更侧的包、未变更侧自动沿用上一版（沿用来源随包存证，供审核聚焦变更）。
- US-V3 开发者看数据。验收：游戏维度报表（进房/局数/流水/结算失败率），T+1；隐私脱敏（不含玩家个体标识）。
- US-V4 开发者对账与结算。验收：日账单按 `round_id` 聚合净流水；月结算单（分成参数见第 6 章）可导出；争议账单可提工单按回合溯源。
- US-V5 SDK 体验。验收：官方脚手架（模板仓库 + 本地模拟器）新游戏 10 分钟出可跑 demo；SDK 版本兼容矩阵公示，破坏性变更提前一个版本公告。

**依赖现有能力**：game/game_package/review_log 全链路、RBAC 私有角色、`game_round` 数据、S3 上传。

**数据变更**：`developer_bill`/`developer_bill_item`、`developer_profile`（资质与结算账户）。

**埋点**：`dev_register/dev_upload/dev_submit/dev_bill_view`。

### 4.11 管理后台演进

**目标**：在现有 14 页之上补齐"运营台 + 风控台 + 财务台"，权限全部走现有 RBAC 权限点扩展。

| 新页面 | 核心能力 | 优先级 |
|---|---|---|
| 财务对账 | 充值/提现/发放三单查询；渠道对账单导入比对；按 `round_id` 溯源；差异导出 | **P0** |
| 风控工作台 | 规则配置（阈值/动作）、案件池（充值异常/提现异常/游玩异常）、处置（放行/拒绝/限额/封禁） | **P0 v0 / P1 完善** |
| 内容位管理 | content_slot CRUD + 定时 + 灰度 | P1 |
| 活动管理 | 模板/实例/预算/效果 | P1 |
| 工单 | 玩家工单分派与 SLA 计时 | P1 |
| 审核增强 | 审核时长 SLA 计时、大额或高风险包双人复核 | P1 |

**规则**：所有敏感操作（调账/提现审批/风控处置）二次确认 + 写 `audit_log`（现有机制）；玩家余额调账维持现状（player-only + 确认）。

### 4.12 合规与风控（P0，贯穿性专章）

**目标**：把"真钱平台底线"做成产品能力，而不是合规部门的口头要求。

**1) 实名/KYC 分级**
- Lv0 未实名：仅体验，单日充值 ≤0、不可提现（M1 起充值即强制 Lv1）。
- Lv1 身份证二要素：充值日限 3,000 元。
- Lv2 人脸核身 + 绑卡：解锁提现，日提现 10,000 元。
- 验收：限额在**下单/申请入口**前置拦截并给出提额指引；限额值配置化（`risk_rule`）。

**2) 未成年人保护**
- 实名识别年龄 <18：禁止充值与提现、游玩时段限制（20:00-21:00 之外禁入）、充值退款流程（家长申诉 → 核实 → 原路退回 → 账户冻结）。
- 验收：未成年账号任何资金入口返回明确拦截文案；退款案件 72h 响应。

**3) 负责任游戏**
- 充值限额（日/周/月，玩家自设只能下调）、单局限额（游戏配置声明 + 平台校验）、连续游玩 60 分钟强制休息提醒、冷静期（24h/7d，期间禁充值）、自我排除（3/6/12 个月，期间禁登录资金功能）。
- 验收：全部入口可从"账号与安全"一键设置；冷静期/排除期**不可自助提前解除**（客服通道需人工+等待期）。

**4) 反洗钱与异常风控规则引擎**
- 规则示例：快进快出（充值后 <10min 提现 ≥80%）、拆分充值（同卡多笔贴近限额）、夜间大额、新号高额、RTP 异常游戏（实际 RTP 偏离声明超阈值）。
- 命中 → 生成 `risk_case` → 工作台处置（放行/延迟打款/拒绝/上报）。
- 验收：规则配置化生效 ≤5 分钟；每条处置写审计；打款前强制过规则引擎。

**5) 游戏公平性治理**
- 包审核扩展：RTP/概率配置作为 `game_package` 提交物**哈希存证**（不可篡改、可追溯版本）。
- RNG 收口：平台向 goja 注入统一随机源，bundlesec 检测并拒绝脚本覆写 `Math.random`。
- 上架后监控：日终比对实际 RTP 与声明值（数据源 `game_round` 聚合），偏离超阈值自动生成风控案件并可一键下架。
- 验收：任何在线游戏的概率配置可追溯到审核存证哈希；RTP 漂移告警 T+1 内可见。

**6) 个人数据与隐私**
- 最小化收集（身份证号只存哈希+尾号）、玩家数据导出、注销删除（财务留存除外，见 US-A5）。

**7) 游戏内容复审（上架后抽检）**
- 上架游戏按周抽检：素材合规（无赌博暗示/低俗/侵权）、玩法与审核版本一致（前端包哈希与审核存证比对，复用 4.12-5 的存证机制）。
- 抽检不合格 → 生成工单 → 限期整改 → 未整改自动下架并公示。
- 验收：包哈希与审核存证不一致的大厅游戏，T+1 内被识别并置灰下线。

**依赖现有能力**：`bundlesec.Validate`（扩展规则）、`game_round` 聚合、`audit_log`、审核工作流。

### 4.13 客服与信任（P1）

**用户故事**
- US-C1 帮助中心。验收：FAQ/规则/流程公示（充值、提现、审核标准、限额政策）；检索可用。
- US-C2 工单。验收：分类（资金/游戏/账号/其他）；资金类 SLA 24h 首响、72h 结案；超时升级。
- US-C3 资金争议处理。验收：客服工具可按 `round_id`/`order_no` 溯源全链路（复用三表关联与 `game_round_operation` 失败留痕）；补偿走 `grant_batch` 留痕。
- US-C4 透明度公示。验收：游戏审核结果公示（名称/开发者/通过时间）、RTP 声明页、中奖播报真实性说明。

## 5. 经济系统设计专章

### 5.1 货币模型

- 单币种「金币」，即现有 `balance`（int64 最小单位），1 元 = 100 金币。
- M1 不引入子余额（可提现/赠送拆分），以"充值返"活动替代"体验金"，避免污染提现口径；子余额作为 P2 评估项（见 4.2 开放问题）。
- 多币种预留：新增表统一带 `currency` 字段（默认 `CNY`），`player_balance` 暂不加列。

### 5.2 货币流向图

```
                 ┌──────────── 平台投放（受预算约束）────────────┐
                 │  活动奖励 / 签到 / 任务 / 升级权益 / 救济金     │
                 ▼                                              │
玩家 ──充值──► balance ──beginRound/deduct──► 游戏回合 ──reward──► balance
 │                                            │                    │
 │                                            └─ 净输值（平台留存）  │
 └──────────────提现（Lv2，T+1，手续费1%）◄────（审核+风控）◄────────┘

回收渠道：游戏净输值留存、提现手续费、券过期作废、活动预算未核销
投放渠道：活动/签到/任务/升级奖励（全部走 grant_batch，逐笔流水）
```

### 5.3 投放/回收平衡表（初始参数）

| 渠道 | 触发 | 预算约束 | 备注 |
|---|---|---|---|
| 首充礼包 | 首笔充值 | 100% 返 ≤6 元档 | 一次性，幂等 |
| 充值返 | 档位充值 | 返 3%-8%，活动预算内 | 模板化配置 |
| 亏损救济金 | 周净输 ≥100 且 VIP≥1 | 周投 ≤ 平台周流水 1% | 走 VIP 权益，明示规则；M2 起生效（依赖 VIP 上线，评审 F7） |
| 签到/任务 | 日活 | 日投 ≤ 日活 × 0.5 元 | 手动领取 |
| 升级奖励 | 等级达成 | 一次性小额定值 | 曲线见 US-G1 |

### 5.4 通胀护栏与异常处置

| 护栏 | 阈值 | 越界动作 |
|---|---|---|
| 日投放/日回收比 | < 0.85 告警，< 0.7 冻结新活动 | 运营复核投放策略 |
| 平台总投放/总流水 | ≤ 5% | 财务审批后放开 |
| 单玩家日净流入（非充值来源） | ≥ 500 元生成风控案件 | 规则引擎处置 |
| 实际 RTP 偏离声明 | ±2pct 持续 3 天 | 风控案件 → 可下架 |
| 异常提现比（驳回/申请） | > 10% 告警 | 风控策略复盘 |

## 6. 商业模式与变现设计

### 6.1 方案对比

| 方案 | 内容 | 利 | 弊 |
|---|---|---|---|
| A 流水分成（主推） | 平台抽游戏净流水 20%-30%，开发者 70%-80% | 与开发者激励一致；对账天然按 round_id | 收入随流水波动 |
| B 会员订阅 | 玩家 VIP 订阅费 | 现金流稳定 | 与资金合规交叉，弱化主业务 |
| C 广告/推广位 | 开发者买推荐位 | 边际成本低 | 伤害分发公平性，仅作补充 |

**主推 A + C 补充**：流水分成为主体，推荐位作为运营工具对优质开发者减免，不做竞价排名。

### 6.2 分成参数（写入 `game` 审核存证，公平性治理范围）

- 阶梯：开发者月净流水 <10 万 → 70%；10-100 万 → 75%；>100 万 → 80%。
- 平台抽成实现：游戏脚本在 `reward` 计算中按声明比例执行；平台侧在 `CommitRound` 记录回合净流水，日终与声明 RTP/抽成对账（偏离即风控案件，见 4.12-5）。
- 提现手续费 1% 归平台（支付通道成本之上）。

### 6.3 对经济系统的约束

分成比例与 RTP 声明同属包审核存证：改动任一参数 = 新版本包 = 重新审核，杜绝"后台偷偷改概率/改抽成"。

> 开放问题（抽成执行路径）：方案① 脚本按声明比例执行 + 日终对账兜底（对现状引擎零改动，M1 采用）；方案② 平台在 `CommitRound` 强制扣减抽成（更可信，但改结算语义）。M1 技术评审定稿，PRD 先按①设计并保留②的升级空间。

## 7. 数据字典增量

### 7.1 现有表加列（迁移项）

**player**

| 列 | 类型 | 说明 |
|---|---|---|
| phone | varchar(20) nullable | 绑定手机 |
| level / exp | int / bigint | 成长（P1） |
| vip_level | int default 0 | P1 |
| kyc_level | smallint default 0 | 0/1/2 |

## 8. 关键流程图（文字版）

### 8.1 玩家资金全链路（含异常）

```
注册 ──► 实名 Lv1（拦截点：未实名不可充值）
  │        └─失败: 提示原因, 可重试; 3次失败转人工
  ▼
充值: 选档 ──► payment_order(created) ──► 渠道支付
  │        ├─回调验签成功 ──► succeeded ──► 幂等入账(recharge:{order_no})
  │        │        └─余额事件推送(现有 wallet:balance, version 递增)
  │        ├─回调超时 ──► 主动查单补偿(分钟级)
  │        └─渠道成功但未入账 ──► T+1 对账补单 + 告警
  ▼
游玩: beginRound ──► deduct/reward 入队 ──► endRound = CommitRound
  │        └─失败: endRound=false, game_round_operation 留痕, 客服可溯
  ▼
提现: 申请(Lv2, 限额校验, 风控规则) ──► 申请即全额扣款(withdraw:{withdraw_no})
  │        ├─人工审核通过 ──► 打款 ──► paid
  │        ├─驳回 ──► 退回流水(withdrawal_refund) + 通知
  │        └─打款失败 ──► failed 自动退回 + 告警
```

### 8.2 开发者接入上架

```
注册开发者 ──► 资质提交 ──► 开通(auto-provision: user→developer→私有角色)
  ▼
创建游戏(选分类) ──► 上传前端包(zip→bundlesec→S3) + 后端 JS(bundlesec)
  │        └─bundlesec 即时反馈: 概率声明存证哈希 / Math.random 覆写检测
  ▼
提审 ──► 人工审核(≤24h P75, 驳回原因结构化) ──► approved
  ▼
大厅可见(缓存失效) ──► 产生 game_round ──► 日账单 ──► 月结算(T+15)
```

### 8.3 充值三方对账（日任务）

```
渠道日账单 ⇄ payment_order ⇄ player_transaction(type=recharge)
  ├─单边账(渠道有/平台无) ──► 补单(幂等) + 告警
  ├─单边账(平台有/渠道无) ──► 冻结案件 + 人工核查
  └─金额不一致 ──► 差异单导出, 财务处理
```

### 8.4 游戏回合资金流（现状沿用，零改动）

`beginRound`（服务端生成 round_id）→ `deductBalance/rewardBalance` 入队 → `endRound` = `CommitRound`（PostgreSQL 事务写 game_round + game_round_operation + player_transaction.round_id，幂等键防重）→ 提交后余额事件 → WS 推送（version 单调守卫）。

## 11. 迭代路线图（3 个里程碑）

### M1 · 经济闭环与合规底线（10 周两波交付，P0）

- **范围**：充值闭环（订单/回调/幂等/查单补偿）、平台发放（批次）、提现 v1（人工审核）、三方对账、实名分级、负责任游戏限额 v1、风控规则引擎 v0 + 案件池、财务对账页、大厅发现（推荐位/收藏/最近/富详情页/中奖播报）、账户基础（找回密码/多端互踢/注销）、埋点基座、首充礼包。
- **波次交付**（评审修正：原 8 周排期超载，修正为 10 周两波）：**M1a（第 1-5 周）**——充值闭环、平台发放、实名 Lv1、流水与财务对账页 v1、埋点基座；前置依赖：支付渠道签约与沙箱就绪（拍板项 D2，未就绪整体顺延）；Go/No-Go 闸门：注册→实名→充值→游玩→流水可查 e2e 通过后进入 M1b。**M1b（第 6-10 周）**——提现 v1、负责任游戏限额、风控引擎 v0 + 案件池、大厅发现、账户基础、首充礼包、中奖播报、公平性存证（`game_package` 加列 + 审核流程接入哈希存证，自 M1b 起新包即存证）。
- **明确不做**：提现自动打款、活动模板化、成长体系、社交、锦标赛、开发者自助门户（M1 沿用管理员代建 + 人工月结）、多端 SDK 破坏性变更；资金争议走"对账页溯源 + grant 补偿"最小能力，工单系统在 M2。
- **验收标准**：① e2e 全链路通过：注册→实名→充值→游玩 100 局→提现到账（对齐 `docs/测试提示词.md`）；② T+1 对账差异 = 0；③ 结算差错率 = 0；④ 未实名/未成年全部资金入口被拦截且有可读文案；⑤ 375px 全新页面可用；⑥ 重复支付回调 1000 次仅入账一次；⑦ 未实名玩家无法进入充值页（前置拦截，评审 F11）。

### M2 · 增长与生态（10 周，P1）

- **范围**：等级/签到/任务/VIP、活动模板化（4 个模板）、券与礼包码、通知中心、数据看板、灰度开关、房间大厅 UX、机器人填充、开发者自助门户 + 脚手架 + 日账单、游戏内体验补全（新手引导/规则/战绩/举报）、风控工作台完善、配置失效广播、手机绑定、i18n 框架。
- **明确不做**：锦标赛、好友/聊天、回放、多币种、体验包子余额拆分。
- **验收标准**：① 运营零发版上线一个完整活动并复盘 ROI；② 新开发者 10 分钟跑通 demo（以 slot-game 为基准实测）；③ D7 相对 M1 留存基线 +3pct；④ 房间创建→等待室→开局→结算全流程 e2e 通过。

- **范围**：锦标赛、好友/房间聊天/人气榜、回合回放、多语言首批语种、多币种落地、体验金子余额方案评估、提现自动打款（风控通过件）、公平性可验证 RNG 全量上线。
