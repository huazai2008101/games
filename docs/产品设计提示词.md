第一步 · 先读懂现状（不许凭空设计）
==========================================================

设计必须建立在以下已验证的技术事实上（与 docs/architecture.md 一致）。
动手设计前请先抽查代码印证，不得虚构或修改这些事实：

1. 服务拓扑（Go 单仓多服务，Go + Gin + GORM + PostgreSQL + Redis，DI 用 uber-dig）：
   - storage  :9000  内置 S3 兼容对象存储（游戏前端包托管）
   - admin    :8080  管理后台 API
   - lobby    :8081  玩家大厅 API
   - game-api :8082  游戏 WebSocket 网关 + goja 游戏引擎（Actor 模型）
2. 双身份域（不可打破的架构约束）：管理端 user（RBAC + developer 私有角色）
   与玩家 player 完全隔离，各自独立 JWT 体系。
3. 数据模型：18 张表（user / developer / game_category / game / game_package /
   game_round / game_round_operation / review_log / audit_log / role / permission /
   menu / role_permission / user_role / user_permission / player /
   player_balance / player_transaction）。
4. 游戏接入方式：开发者上传"前端 bundle（zip → S3 → 大厅 iframe 加载）+
   后端 JS（goja 沙箱执行）"，经 bundlesec 安全校验 + 人工审核
   （draft → pending_review → approved/rejected → archived）。
5. 会话模式：quick（自动匹配）、room（房主房间码）已实现；tournament 仅预留未实现。
6. 资金链路（平台最强资产，设计中绝不可弱化）：
   - 游戏脚本显式 beginRound/endRound，endRound 是唯一结算提交点，
     round_id 仅由服务端生成，拒绝客户端传入
   - player_balance 非负约束 + player_transaction 幂等键唯一 + round_id 贯穿
   - game_round / game_round_operation 全量审计（失败操作也留痕，可对账）
   - 实时余额推送：事务提交后 Redis Pub/Sub → WS `wallet:balance`
     （version 单调守卫，按环境隔离）
   - 三重兜底对账：每局结果自带权威余额 / 重连后 balance:query / 页面恢复可见对账
7. SDK：
   - game-frontend-sdk：GameClient + GameLifecycle，事件驱动，TypeScript
   - game-backend-sdk：platform API（beginRound/endRound/deductBalance/rewardBalance/
     getBalance/broadcast/sendTo/getPlayerIDs/setGameState/setTimeout/setInterval）
8. 前端现状：
   - 大厅仅 5 页：Home（分类导航 + 搜索 + 游戏列表）/ Login / Register /
     Profile（资料/余额/流水）/ GamePlay（iframe + WS）
   - 大厅 API 已有：注册/登录/刷新/登出、分类列表、游戏列表（分页/搜索/分类过滤）、
     游戏详情、玩家资料/余额/流水
   - 管理后台 14 页：Dashboard、开发者、游戏、游戏版本包、分类、审核、余额调账、
     玩家、玩家流水、审计日志、角色、权限、菜单
9. HTTP 契约：原生 HTTP 语义（无 {code,message,data} 包裹），错误信息经
   X-Error-Message 响应头；WebSocket 消息保留事件信封。
10. 术语与原则：余额统一叫 balance（不说"点数"）；资金路径零阻塞（发布异步化）；
    敏感配置走环境变量；分类是平台级主数据（game_category 单源）。

请再自行抽查这些代码入口印证现状（只读，不修改）：
- backend/internal/app/{admin,lobby,game}/handler|route|gateway/  各端路由与处理器
- backend/internal/domain/service/wallet.go  资金领域服务
- backend/internal/domain/model/  18 张表实体
- frontend/lobby/src/views/  frontend/admin/src/view/  两端页面
- sdks/game-frontend-sdk/src  sdks/game-backend-sdk/src  双 SDK 能力面
- examples/slot-game  官方示例游戏（开发者接入体验的基准线）

若抽查中发现代码与上述事实不符（代码在快速演进），一律以代码为准，
并在 PRD 的现状盘点章节标注差异，同时反向修订本文档相应事实。

第二步 · 产品定位（先给结论，再展开论证）
==========================================================

1. 一句话定位：一个"资金安全级"的 H5 即开游戏聚合平台——
   玩家 3 秒开玩、开发者 10 分钟接入、运营每一步可配置可度量可回滚。
2. 目标用户画像（至少 4 类，每类给出：目标 / 痛点 / 关键场景 / 设计启示）：
   - 休闲玩家：碎片时间、手机端、低门槛即开即玩
   - 沉浸玩家：多局成长、荣誉比较、追大奖
   - 游戏开发者：个人/小团队，关心接入成本、分成收益、数据反馈
   - 平台运营/审核：效率工具、风险控制、合规留痕
3. 北极星指标 + 护栏指标（自行定义并说明选择理由），参考方向：
   - 北极星：周活跃有效玩家数（有真实游玩轮次）或周付费玩家数
   - 护栏：结算差错率 = 0、余额类客诉率、首局转化率、D1/D7 留存、
     游戏审核时长、支付成功率
4. 商业模式（先想清楚再设计功能）：平台自身如何盈利——游戏流水抽成 /
   开发者分成差价 / 会员订阅 / 增值服务等，给出主推模型与备选，
   并说明它如何反向约束经济投放节奏与开发者分成比例。
5. 竞品校准：对标 2-3 个同类产品（H5 游戏中心 / 休闲游戏聚合平台），
   只输出与本项目现状相关的差异化结论（功能取舍与体验基准），不做通用市场报告。
6. 产品原则（每条功能设计都必须能回答）：
   - 资金安全 > 合规 > 体验 > 功能数量
   - 移动优先：首屏到可玩 ≤ 3s，断线可恢复，异常重来不多扣一分钱
   - 玩家的每一分钱都有 round_id / 幂等键可追溯；运营的每一步都有审计与灰度
   - 平台价值 = 玩家体验 × 开发者收益，双边都要有"赚到了"的感觉
   - 合规是底线约束，不是可选项

第三步 · 差距清单（现状 vs 完美平台）
==========================================================

按以下八个维度盘点差距。每条差距标注 [P0/P1/P2] 与优先级理由：
P0 = 没有它平台不成立或有资金/合规风险；P1 = 显著影响增长与留存；P2 = 体验增强。

A. 资产闭环（当前最大缺口，P0）
   现状：玩家余额唯一来源是管理端人工调账，经济闭环断裂，无法自运转。
   需设计：充值（支付渠道抽象 + 充值订单 + 回调幂等 + 对账单）、
   提现/兑换、平台发放（活动奖励/补偿/礼包码/新人礼）、亏损返还等资金入口，
   全部复用现有幂等键 + 事务 + 审计 + 非负约束，绝不出现绕过
   player_transaction 的余额变更路径。

B. 大厅发现与分发（P0 基础 / P1 增强）
   现状：分类导航 + 基础搜索 + 游戏列表（Redis 缓存），有游戏详情接口。
   需设计：运营推荐位/Banner、收藏、最近在玩、榜单（人气/新游/中奖播报）、
   富游戏详情页（截图/规则/RTP 声明/在线人数/开发商）、标签体系、
   新游孵化位。推荐冷启动给出明确策略（热门兜底 → 行为召回）。

C. 游戏内体验（P1）
   需设计：新手引导、规则与帮助入口、历史战绩、断线重连 UI 状态机
   （对齐现有 reconnect/balance:query 能力）、音效画质设置、游戏内播报、举报入口。

D. 多人玩法（P1）
   需设计：房间模式的大厅 UX（等待室/成员列表/准备/房主控制面板，
   补齐 architecture.md 已声明的缺口）、tournament 落地方案（复用 quick/room
   会话模型）、低人气游戏的机器人填充策略、观战互动。

E. 玩家成长与社交（P1/P2）
   需设计：等级/经验、签到、任务/成就、VIP 体系、排行榜、好友、
   聊天（含骚扰防护与敏感词分寸设计）、通知中心。

F. 运营系统（P1）
   需设计：公告/Banner/活动配置（开关 + 定时 + 人群定向）、推送触达、
   券与礼包、数据看板（留存/转化漏斗/LTV/游戏健康度）、A/B 与灰度开关；
   所有运营操作复用 audit_log 审计。

G. 开发者生态（P1）
   现状：开发者由管理员代建账号，无自助入口；接入基准 examples/slot-game。
   需设计：开发者自助门户（注册 → 创建游戏 → 上传 → 提审 → 数据 → 结算，
   复用现有 developer + 私有角色 RBAC）、接入文档与本地调试工具、
   分成结算与账单（给出 2-3 个分成模型方案及利弊）、游戏健康度报表。

H. 合规与风控（真钱平台底线，P0）
   需设计：游戏公平性治理（RTP/概率配置的审核存证、可验证的随机数机制、
   公平性对外公示）、实名/KYC 分级（额度分级解锁）、未成年人保护（识别 + 限制 +
   家长退费流程）、负责任游戏（充值/时长限额、冷静期、自我排除）、
   反洗钱规则引擎（快进快出/拆分交易/异常提现）、异常投注与羊毛党风控、
   个人数据与隐私合规（最小化收集、玩家数据导出与删除）、
   游戏内容复审机制（上架后抽检）。

第四步 · 分模块设计要求（每个模块都要写到这个深度）

模块清单：
1. 账户与身份：注册登录强化（手机/邮箱/三方登录可选）、找回密码、
   多设备管理（互踢策略）、账号注销。
2. 钱包与经济系统：货币模型（单币种起步，多币种预留）、充值/提现全流程、
   发放与回收、经济投放/回收平衡表、通胀护栏指标（如日投放/日回收比、
   付费渗透率对投放的约束）。
3. 大厅与游戏发现：信息架构（首页布局分区）、推荐策略冷启动方案、
   搜索（联想/纠错/空结果运营位）。
4. 游戏会话体验：进游戏前/中/后全流程状态机；断线/刷新/多端登录策略；
   与现有 actor 会话模型（created→waiting→ready→playing→finished）对齐。
5. 多人与赛事：quick/room/tournament 在统一会话模型下的差异化设计。
6. 成长与激励：数值曲线给出示例表（等级经验表、签到奖励表、任务池样例），
   数值必须可被经济模型约束。
7. 社交系统：隐私与防骚扰机制先行（黑名单/举报/敏感词）。
8. 运营与增长：活动模板化（首充/返水/锦标赛/节日活动），
   明确"配置化程度"要求——运营侧不发版可完成。
9. 开发者平台：接入旅程目标 ≤ 10 分钟跑通 demo（以 slot-game 为基准）；
   分成结算模型与账单周期。
10. 管理后台演进：在现有 14 页基础上补——内容运营位管理、活动管理、
    风控工作台、财务对账（round_id 对账单导出）。
11. 客服与信任：帮助中心、工单、资金争议处理 SLA、透明度公示
    （游戏审核结果公示、RTP 声明）。

第五步 · 体验硬性标准（输出前逐条自检）
==========================================================

- 每个页面必须有四种状态设计：loading、空状态、错误态、断网恢复态

- 移动端 375px 宽度全部可用；横竖屏策略明确
- 文案用玩家语言，不出现内部术语（round/session/actor/幂等）
- 多语言架构预留（i18n key 规范），首期可只出中文
- 所有实时消息对齐现有 WS 事件信封风格；余额显示必须遵守 version 单调守卫
