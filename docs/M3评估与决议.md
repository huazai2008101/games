# M3 收尾评估：锦标赛 / 回放 / 可验证 RNG

> 结论先行：**「可验证 RNG」核实后确认已实现**（见 §3，无需新开发）；
> **锦标赛与回放建议缓发**，理由与前置条件如下。当前产品（M1+M2 全部）
> 已达到可交付部署运营状态。

## 1. 锦标赛（tournament）——建议缓发，前置条件未成熟

**工作量**：大（3-4 周）。报名/退费资金流、赛程调度器（淘汰/积分）、
奖金池聚合与 `grant_batch` 发放、人数从 8 到 256 的并发会话编排、
专用的 admin 运营页与玩家端赛程页。

**缓发的决定性理由**：平台当前在架游戏全部是单人 quick 模式（slot 示例），
**没有任何多人游戏可以承办锦标赛**。先建赛制、后建游戏供给，是本末倒置。

**启动前置条件**（满足其一即可启动）：
1. 至少 2 款 room/tournament 模式的多人游戏过审上架；
2. 或外部开发者通过门户（已上线）提交了首个多人游戏。

启动时的实现路径已经铺好：`tournament` 会话模式枚举已预留，
报名费可走 `PaymentService` 同款平台单操作幂等路径，
奖金发放直接复用 `GrantService` 批次（幂等键 `tournament:{entry_no}` 已在 PRD 定义）。

## 2. 回放（game_replay）——建议缓发，现有对账能力覆盖核心诉求

**工作量**：中（2 周）。引擎事件流落存（每回合 JSON 流 +
对象存储归档）、按 round_id 还原播放的前端、存储成本评估。

**缓发的理由**：资金争议的核心诉求是「这笔钱为什么扣/为什么给」，
现有的 `game_round` + `game_round_operation`（含失败留痕）+
`player_transaction.round_id` 三表关联**已经能完整回答**——
M1a 验收时财务对账页已验证按回合溯源。回放解决的是「游戏过程还原」，
属于客服体验增强而非争议仲裁的必需品。

**启动时机**：客服工单（M2 未含）上线后，若资金争议中出现
「过程性争议」（如"我没点这一把"）占比显著，再立项。
实现时优先评估「每回合事件 JSON 存 S3」的廉价方案而非建表。

## 3. 可验证 RNG——核实确认：已实现 ✅（无需开发）

PRD 4.12-5 拆解的三个子项逐一核实：

| 子项 | 状态 | 证据 |
|---|---|---|
| 平台统一随机源，脚本不可绕过 | ✅ 已实现 | `engine/sandbox`：goja VM 内 `Math.random` 被替换为 CSPRNG（crypto/rand 53 位均匀分布），`platform.random` 同源；熵读取失败直接 panic（fail-closed），由引擎 supervisor 恢复上报 |
| bundlesec 检测概率配置篡改 | ✅ 部分实现 | 上传期静态扫描（`bundlesec.Validate`）+ 公平性存证（v0007：`bundle_hash`/`rtp_declared` 审核固化，改动即重新审核）+ RTP 漂移监控（数据字典中 `game_round` 聚合路径已具备，M2-4 看板的 game-health 端点即其数据源） |
| 可验证（玩家可自行验证单局公平） | ⏸ 唯一剩余项 | 需要 commit-reveal 随机链（每回合预告 seed 哈希、结算后揭示），涉及 SDK 破坏性变更（PRD 明确 M2/M3 前不做 SDK breaking change） |

**建议**：commit-reveal 随机链列为 v2 信任增强项，与「游戏内公平性验证页」
一起做（预计 1.5 周 + SDK minor 版本）。当前 CSPRNG + 存证 + 漂移监控
的组合已满足「平台不作恶可审计」，commit-reveal 补的是「玩家可自行验证」，
属于信任的锦上添花而非底线。
